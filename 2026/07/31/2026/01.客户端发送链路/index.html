Pulsar 客户端发送链路

主线起点。搞清你在代码里写 producer.send("hello") 之后，这一条消息在客户端内部经历了什么，
直到变成网络上的字节流。

学习目标

  • 理解 Pulsar 客户端”同步 API 是异步的薄包装”这一贯穿全栈的模式
  • 掌握 batching（批量）、背压、有序性、sequenceId 四个机制在发送路径上的落点
  • 看懂协议帧的二进制结构

相关代码（按阅读顺序）

文件 内容
pulsar-client/.../impl/TypedMessageBuilderImpl.java 发送入口
pulsar-client/.../impl/ProducerImpl.java 发送核心
pulsar-common/.../protocol/Commands.java 协议命令构造（客户端/broker 共用）

1. 完整调用链

2. 入口：TypedMessageBuilderImpl.send()

两个关键点：

  1. 同步 = 异步的薄包装。send() 就是 sendAsync().get()。这个模式贯穿 Pulsar 全栈：客户端 API、broker、存储层，所有”同步方法”都是异步方法的包装。
  2. **triggerFlush()**：如果 future 没完成，说明消息进了批量容器还没凑满，同步调用不能干等，主动把当前批次发出去——用牺牲批量效率换同步调用的低延迟。

3. 核心：ProducerImpl.sendAsync(msg, callback)

这个方法做四件事：

  1. 状态校验：producer 是否处于可发送状态（isValidProducerState）
  2. 背压限流：canEnqueueRequest 检查信号量，队列接近上限就拒绝（配置 blockIfQueueFull）
  3. 压缩：开启压缩则压缩 payload（applyCompression）；批量模式下压缩延迟到批次关闭时做
  4. 分块（chunking）：超大消息切成多个 chunk，每个 chunk 单独发送，带 chunkId / totalChunks 元数据

4. 分叉点：批量 vs 单条（serializeAndSendMessage）

注意 canAddToBatch 的排除条件：延迟投递消息（hasDeliverAtTime）必须单独发，不能进批次。

5. 在途队列与有序性（processOpSendMsg）

三个机制各司其职：

机制 作用
pendingMessages 在途队列 存”已发出、等 broker 确认”的消息。队列满 = 背压。
updateLastSeqPushed sequenceId 推进，是消息去重的基础（配合 broker 端）
eventLoop().execute(...) 同一 producer 的所有写由同一个 Netty 线程串行执行

核心认知：顺序不是靠锁，是靠线程模型。这是 Pulsar 单 producer 消息有序的根本原因。

6. 协议帧构造（Commands.newSend + serializeCommandSendWithSize）

  • 帧最外层是总长度前缀：TCP 是字节流，接收方靠它划帧（知道一条消息在哪结束）
  • CMD 是 protobuf 的 BaseCommand，类型 SEND，带 producerId、sequenceId、numMessages
  • CHECKSUM 用 CRC32C，按 broker 协议版本兼容降级为无校验
  • 这段代码在 pulsar-common 模块：客户端和 broker 共用同一份编解码，这就是”协议”的物理载体

7. 五个关键设计（本课精华）

  1. 同步 API 是异步的薄包装 —— 全栈统一的模式
  2. Batching 发生在客户端 —— 多条消息合成一个 SEND 命令（numMessages > 1），满批次或定时触发
  3. 背压 = 在途队列 + 信号量 —— blockIfQueueFull 配置的源码真相
  4. 有序性靠单线程写 —— event loop 串行，不靠锁
  5. sequenceId 是一等公民 —— 协议帧、在途队列、去重逻辑里反复出现；broker 靠它识别重复，客户端靠它匹配 ack

自查问题

1. 为什么同步 send() 方法里还要调 triggerFlush()？

同步调用不能等批次攒满。消息进 batch 容器后 future 未完成，说明在等更多消息凑批；
triggerFlush() 强制把当前批次发出去，保证同步调用的延迟可预期。

2. 连接断开时，pendingMessages 里的消息会怎样？

不会失败、不会丢弃，留在队列里等重连。重连成功后：
connectionOpened → 重新注册 producer → resendMessages 把 pending 消息带原 sequenceId 重发。
broker 端靠 sequenceId 去重，所以重发不产生重复（至少一次语义）。
超过 sendTimeoutMs（默认 30s）仍未确认，则 failPendingMessages 用超时异常完成回调。

3. 协议帧里为什么要有 TOTAL_SIZE 长度前缀？

TCP 是字节流不是消息流，接收方天然不知道”一条消息在哪结束”。长度前缀用来划帧：
读满 TOTAL_SIZE 字节即一个完整帧，可直接反序列化，避免半包/粘包问题。
