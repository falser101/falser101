Pulsar Managed-Ledger ② 写入路径

上一课结尾的问题：broker 调用的 asyncAddEntry() 到底做了什么？本课完整走一遍写入路径：
从 ManagedLedgerImpl.asyncAddEntry 到 OpAddEntry，再到真正写进 BookKeeper、分配位置、通知上层。

学习目标

  • 掌握写入路径的完整调用链
  • 理解有序性的三层保险：单线程入口 + FIFO 队列 + 完成也串行
  • 搞清楚”单线程”的真相：共享线程池 + 按名字哈希绑线程
  • 理解位置（LAC）由谁分配、何时分配
  • 看到写成功后的完整闭环：读缓存、推进 LAC、唤醒消费者、回调 broker

2. 有序性：三层保险

  1. 单线程入口：executor.execute(() -> internalAsyncAddEntry(op)) —— 所有写操作先跳转到
    ML 专属的一个线程，天然串行。
  2. FIFO 队列：pendingAddEntries.add(op) —— 进来的顺序就是排队的顺序。
  3. 完成也串行：BookKeeper ack 后，addComplete 里再次 ml.getExecutor().execute(this)，
    在同一个线程出队下一个。

所以一个 ML 的写入是严格按提交顺序落盘的。这也解释了 broker 为什么用 topicOrderedExecutor
串行化同一 topic 的操作：存储层本身就是串行的，上层必须配合。

“单线程”的真相：共享池 + 哈希绑线程

“单线程入口”不是每个 ML 一条专用线程，而是 BookKeeper 客户端主工作池里按名字哈希绑定的线程。
证据链：

线程池的大小来自 BookKeeper 配置 numWorkerThreads，默认 = CPU 核数。

说法 对不对
每个 topic 一个专用线程 ❌ 没有专用线程，是共享池
整个 broker 只有一个线程 ❌ 池子有 N 个线程（默认 CPU 核数）
每个 ML 在共享池里固定绑定一个线程 ✅ 准确说法

为什么这么设计：

  1. 顺序按 ML 粒度保证，不靠全局锁：同 ML 永远同线程，异 ML 天然并行，比”一把大锁串所有写”吞吐高。
  2. 线程数与 topic 数解耦：几千个 topic 也只占 N 条线程，numWorkerThreads 可控。
  3. 代价（noisy neighbor）：两个热门 topic 哈希到同一线程时，会互相挤占该线程执行时间——哈希路由的经典权衡。
  4. 和 broker 端同构：第 02 课的 topicOrderedExecutor.executeOrdered(topicName, ...) 是同一个
    OrderedExecutor 模式。整个 Pulsar 的”有序性 = 名字哈希到线程”是统一的设计语言。

补一句：pendingAddEntries FIFO 队列的意义正在于此——当那条线程正忙（比如等新 ledger 创建完成），
后续写入在队列里排队，顺序不乱。队列 + 单消费者线程，缺一不可。

LAC（Last Added Confirmed）是本课最重要的概念：它是”最后一个确认落盘的位置”。
消费者只能读到 LAC，读不到”已发起、未确认”的 entry。这带来：

  • 消费者永远看不到半条数据（一致性）
  • 即使 bookie 故障，已确认的数据都是真实持久化的

4. 写成功后发生什么（完整闭环）

注意最后两行：回调 broker → broker 发 SendReceipt 给客户端（第 01 课的 future 完成），
同时 notifyCursors() 唤醒等在 asyncReadEntriesOrWait 上的消费者。
一条消息从”客户端 send”到”客户端收到 ack”，到这里闭环。

5. 写满与失败

写满判定（currentLedgerIsFull），三个维度：

**写满不立即轮转，而是”写完这条再轮转”**——setCloseWhenDone(true)，这条 entry 落盘后
asyncClose → ledgerClosed → 创建新 ledger。这就是下一课的主角。

写失败：rc != OK → handleAddFailure → 状态变 WriteFailed → 进入恢复流程（第 08 课讲 bookie 故障）。

本课精华

  1. 写入顺序 = 共享线程池哈希路由（每 ML 固定绑一条线程）+ FIFO 队列，是线程模型保证的
  2. 位置 (ledgerId, entryId) 由 BookKeeper 分配，entryId 来自写成功的回调
  3. LAC = 消费者可见的上限，保证读一致性
  4. 写成功后：进读缓存 → 推 LAC → 唤醒消费者 → 回调 broker（闭环）
  5. 写满 → 写完当前条再轮转；写失败 → 状态机进 WriteFailed 待恢复

自查问题

1. addComplete 收到 BookKeeper 回调后，为什么还要 ml.getExecutor().execute(this) 再执行一遍？

BookKeeper 的回调跑在 bookie 客户端线程上，不是 ML 线程。若直接在回调线程里操作
pendingAddEntries 队列、更新状态，会与 ML 线程并发，破坏有序性。跳回 ML 专属线程，
保证所有状态变更都在同一个线程上串行发生。

2. 如果 producer 同时提交 100 条消息，它们的 entryId 一定连续吗？

不一定。entryId 由 BookKeeper 按”实际写入顺序”分配。若中途触发 ledger 轮转，后面的消息进新 ledger，
entryId 重新从 0 开始。即使同一个 ledger 内，只要有其他写入失败重试等情况，也可能出现空洞。
顺序由 pendingAddEntries 的 FIFO 保证，但编号连续性不保证。

3. 为什么消费者不能读 LAC 之后的 entry？这保证了什么？

LAC 之后是”已发起但未确认落盘”的数据，bookie 故障时可能丢失。限制读取到 LAC，
保证消费者读到的每条数据都是确认持久化的，不会读到”假数据”——这是读写一致性的基础。

4. ML 的 executor 是"每个 topic 一个线程"吗？它到底是什么？

不是。它是 BookKeeper 客户端主工作池（bookKeeper.getMainWorkerPool()，一个 OrderedExecutor）
里的一条线程，通过 chooseThread(ML名字) 按 hash(名字) % numThreads 绑定。池子共 N 条线程
（numWorkerThreads 配置，默认 CPU 核数），broker 内所有 ML 共享；同 ML 永远落在同一条线程上，
不同 ML 可能共线程但互不破坏各自顺序。
