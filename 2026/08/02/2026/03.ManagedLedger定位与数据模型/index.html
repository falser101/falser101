Pulsar Managed-Ledger ① 定位与数据模型

从这一课进入存储层。managed-ledger 是面试高频考点（存储模型、游标、ledger 轮转都是经典问题），
拆成六课讲。本课解决：为什么需要这一层、四个核心抽象是什么、数据最终怎么组织。

学习目标

  • 说清 BookKeeper 与 ManagedLedger 的分工（面试第一问）
  • 掌握四个核心抽象：ManagedLedger / Position / Entry / ManagedCursor
  • 看懂持久化元数据 ManagedLedgerInfo：一个 ML = 一串 ledger
  • 确认 topic 与 managed-ledger 的对应关系
  • 知道 ManagedLedger 的元数据存哪、怎么存（可插拔元数据存储，默认 ZK）

1. 它在架构里的位置

一句话：**BookKeeper 只提供”分布式追加日志”（写 entry、按 entryId 读），它不懂”队列”**。
ManagedLedger 在它上面补上了队列需要的三样东西：

  1. 游标（Cursor） —— 多个消费者各自记录”我读到哪了”
  2. 数据删除 —— 消费过的数据要能回收（BookKeeper 的 ledger 一旦写入只能整体删）
  3. 保留与回溯 —— retention 策略、按时间/位置回溯

打个比方：BookKeeper 是硬盘，ManagedLedger 是文件系统——硬盘只负责存扇区，文件系统才有
“目录、删除、回收站”这些概念。

面试回答”为什么 Pulsar 要把存储层拆出来”：让消息队列语义（游标/ack/backlog）和分布式存储
（复制/追加/容灾）各自独立演进，存储层可替换（tiered storage 就是证据）。

2. 四个核心抽象

① ManagedLedger —— 追加日志

本质就一个词：append-only。又是熟悉的”同步 = 异步包装”模式——Pulsar 全栈统一。

② Position —— 位置 = (ledgerId, entryId)

这是整个 Pulsar 的坐标系统。消息 ID、游标位置、ack 位置、backlog 计算全部用它表示。
面试标准答案：**(ledgerId, entryId) 二元组，先比 ledger 后比 entry**。

③ Entry —— 数据单元

一条 entry = 数据 + 位置。broker 从存储层读出来的最小单位就是 entry。

④ ManagedCursor —— 游标

游标是”每个订阅一个”。markDelete 是游标的灵魂：它标记”这个订阅确认消费到哪了”，
backlog = 最新位置 − markDelete 位置。（第 05 课详讲）

速查表

抽象 一句话 关键方法/字段
ManagedLedger 追加日志本体 addEntry / openCursor
Position 坐标 (ledgerId, entryId) getLedgerId / getEntryId
Entry 数据 + 位置的最小单元 getData / getPosition
ManagedCursor 每个订阅一个的消费进度 markDelete / getReadPosition

核心洞察：topic 的数据不是一个大文件，而是一串有先后顺序的 BookKeeper ledger。三个直接推论：

  1. 删除的粒度 = ledger：消费完一个 ledger 里的所有数据，整个 ledger 可以删掉
    （BookKeeper 不支持删单条 entry，只支持删整个 ledger）——这是必须分 ledger 的根本原因。
  2. 轮转（rollover）：ledger 写到一定大小就”封存”开新的（第 05 课详讲）。
  3. 游标有独立元数据：markDelete 存哪、怎么存，是第 06/07 课的核心。

两个容易混淆的路径

元数据存储里有两套带 “ledger” 的路径，用途完全不同：

路径 谁写 存什么
/managed-ledgers/... Pulsar 的 MetaStoreImpl ManagedLedgerInfo：ledgers 列表、cursors、markDelete 位置
/ledgers/... BookKeeper 客户端（bookie） BookKeeper ledger 元数据：ensemble、quorum、ledger 状态

数据 vs 元数据的分界

内容 存哪
消息内容（entry 数据） bookie 本地磁盘（journal + entrylog）
ManagedLedgerInfo（ledgers 列表、游标） 元数据存储 /managed-ledgers/...
游标 markDelete 的快照 元数据存储（频繁更新走游标自己的 ledger，第 06/07 课详讲）
BookKeeper ledger 元数据 元数据存储 /ledgers/...

一句话：元数据存储只存”账本结构”（哪些 ledger、游标在哪），数据本身在 bookie 磁盘上。

本课精华

  1. BookKeeper = 硬盘（原始存储），ManagedLedger = 文件系统（队列语义）
  2. 位置 = (ledgerId, entryId)，先比 ledger 后比 entry
  3. 一个 ML = 一串 ledger；删除粒度 = ledger，这就是必须轮转的根本原因
  4. 一个 topic 分区 = 一个 ManagedLedger
  5. 元数据分层：ManagedLedger → MetaStore → MetadataStore（ZK/etcd/…），存于 /managed-ledgers/...

自查问题

1. Pulsar 里一条消息的"地址"是什么？怎么比较两个地址的先后？

(ledgerId, entryId)。先比 ledgerId，再比 entryId。

2. 为什么 BookKeeper 之上还要有 ManagedLedger 一层？

BookKeeper 只提供分布式追加日志（写 entry、按 id 读），不懂队列语义。ManagedLedger 补上：
游标（多消费者各自记录位置）、数据删除（消费过可回收）、保留与回溯。同时让存储层可替换。

3. 为什么一个 topic 的数据要分成多个 ledger？

BookKeeper 只支持整体删除 ledger。若只有一个大 ledger，消费过的数据无法回收，磁盘只增不减。
分成多个 ledger 后，消费完的旧 ledger 可直接删除。轮转还带来其他好处（见第 05 课）。

4. 元数据存储里为什么有两套带 "ledger" 的路径？分别存什么？

/managed-ledgers/... 是 Pulsar 的 ManagedLedgerInfo（ledgers 列表、游标），由 MetaStoreImpl 写；
/ledgers/... 是 BookKeeper 自己的 ledger 元数据（ensemble、quorum），由 bookie 客户端写。
名字都带 “ledger”，但一个是 Pulsar 的队列元数据，一个是 BookKeeper 的副本元数据。

5. 消息内容和它的元数据分别存在哪？为什么这么分？

消息内容（entry）存在 bookie 本地磁盘（journal + entrylog）；元数据（ledgers 列表、游标位置）
存在元数据存储（默认 ZK 的 /managed-ledgers/...）。因为元数据需要跨 broker/bookie 共享与协调
（哪个 broker 拥有 topic、游标进度等），而数据只需按位置读写，放本地磁盘性能最好。
