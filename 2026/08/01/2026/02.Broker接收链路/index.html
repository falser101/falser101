Pulsar Broker 接收链路

第一课的字节流到达 broker 后，ServerCnx 如何还原 SEND 命令，BrokerService（管家）如何管理 topic，
消息最终在 PersistentTopic 里通过检查与去重，进入存储层。

学习目标

  • 认识 BrokerService：broker 端所有 topic 的”登记处”和”加载器”
  • 掌握 producer 注册（handleProducer）与消息发布（handleSend）两条路径
  • 看到 broker 端去重的现场：sequenceId 去重在这里兑现
  • 理解 broker 端的有序性与背压机制，和客户端一一对应

相关代码

文件 内容
pulsar-broker/.../service/ServerCnx.java 连接级处理器，持有本连接的 producers/consumers 表
pulsar-broker/.../service/BrokerService.java 管家：topic 加载/创建/缓存
pulsar-broker/.../service/persistent/PersistentTopic.java topic 对象，发布入口

1. BrokerService：管家

它是 broker 上所有 topic 的”登记处”。关键字段即职责：

字段 职责
topics（name → Future<Topic>） 加载中的登记表，并发去重用
multiLayerTopicsMap（namespace → bundle → topic） 已加载 topic 的三层索引，bundle 是负载均衡迁移的最小单位
owningTopics 本 broker 拥有的 topic
topicOrderedExecutor 每 topic 一个串行执行器——broker 端有序性的来源
managedLedgerStorage 通往存储层的桥
acceptorGroup / workerGroup Netty 网络线程组

getTopic：教科书级并发安全懒加载

规则（代码注释里原话）：缓存命中直接返回 → 元数据存在则强制创建 → 不存在且不创建则返回空 →
否则 computeIfAbsent，失败从 map 移除（下次重试）。

3. 消息发布路径（ServerCnx.handleSend）

注意：这里的 Producer 是 broker 端的 Producer 对象（代表一个客户端连接上的生产者），和客户端的 ProducerImpl 一一对应。协议是对称的，代码也是对称的——两边都按 id 管理 producer/consumer，这也是 Commands 放在 common 模块的原因。

4. 去重现场（PersistentTopic.publishMessage）

三个分支的意义：

状态 含义 处理
NotDup sequenceId 没见过 写入存储（下一课）
Dup sequenceId 见过（重连重发） 不落盘，直接回 SendReceipt
Unknown 无法判定（producer 重连中） 报错，客户端会重试

第一课说”broker 端 sequenceId 去重”就在这里兑现。客户端重发 → broker 去重 → 不产生重复，
这就是 at-least-once（至少一次）语义的完整闭环。

5. 三个值得记住的设计点

  1. 去重的落点在 PersistentTopic，去重状态持久化在名为 pulsar.dedup 的游标上（后面讲游标时会再见到）。
  2. broker 端也有背压：pendingWriteOps + increasePendingSendRequestsAndPublishBytes，和客户端的 pendingMessages 一一对应，构成端到端背压。
  3. 有序性靠线程模型，两端一致：客户端靠 netty event loop 串行写，broker 靠 topicOrderedExecutor.executeOrdered(topicName, ...) 把同一 topic 的操作串行化。再次印证：顺序不是靠锁，是靠线程。

自查问题

1. getTopic 里为什么用 topics map 做"未来即缓存"？不用会怎样？

两个客户端同时第一次发消息到同一个新 topic，若不做合并，会触发两次 topic 加载、创建出两个 Topic 对象，
后一个覆盖前一个导致状态丢失/资源泄漏。用 Future 做缓存，并发请求共享同一个加载过程，只有一个真正执行。

2. 去重返回 Unknown 时，broker 为什么报错而不是落盘？

“无法判定是否重复”时若落盘，而这条消息实际是重连前的重发，就会产生重复消息且无法挽回
（存储层不会二次检查）。报错让客户端重试，等去重状态恢复（producer 重新注册完成）后再判定，
宁可暂时失败，不冒重复风险。
